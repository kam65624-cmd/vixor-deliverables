## 1. الخلاصة التنفيذية

نُفذت الخمس تسليمات كاملة من الخطة المعتمدة (M1, M2, M2b, M3, M4) في مستودعاتها الأصلية دون دمج أو إعادة بناء، ورفعت كـ **5 PRs مسودات مستقلة** مع **CI أخضر مؤكد عبر GitHub API على كل واحد منها**. كما أُغلق بند الأمان الأول بتوثيق نهائي ودمج **PR #13** (إخفاء بادئة سر الويبهوك في اللوجز) بعد إعادة التحقق من الـ diff والـ CI. إجمالي الاختبارات الجديدة المحلية: **~40 حالة اختبار** عبر أربعة مستودعات (كلها خضراء محليًا وعلى CI).

النتيجة المعمارية: دورة النشر «توليد → قرار مخاطر → مسودة → موافقة بشرية → نشر مرة واحدة → سجل نتيجة» أصبحت **مكتملة الكود ومختبرة محليًا**، وتنتظر فقط تهيئة بيئة حية (سر مشترك + قناة اختبار) لتشغيل الإثبات الحي T1. والأهم: أثناء تنفيذ M2b اكتُشفت **ثغرة إنتاجية حقيقية** كانت تجعل فلاتر claim/entry في ناشر تليجرام غير مفعلة إطلاقًا (تفصيلها في §4) — أُصلحت واختُبرت في نفس الـ PR.

## 3. التسليمات بالتفصيل

### M1 — حزمة العقود (vixor-packages / PR #2)
حزمة `@vixor/contracts@0.1.0` **صفر اعتماديات runtime** بمطابقة حرفية لبنود العقد: المغلف الموحد §1 (مع رفض إجباري لأي `schema_version` غير مدعوم)، حمولة `opportunity.detected` §2 (مع إجبار `asset_id` على الصيغة القانونية `chain:address`)، قرار المخاطر §3 مع بوابة `isAssessmentUsableForPublication` fail-closed (allow + valid + غير منتهٍ فقط)، مرشح النشر §4 (حالة الموافقة مثبتة على `pending_human`، أزرار https فقط)، وfixtures حتمية ثابتة الهوية. الاختبارات تعمل عبر `node:test` مع native type stripping — أي بلا أي إضافة للاعتماديات أو تغيير جوهري في الـ lockfile، مع خطوة CI جديدة لتشغيلها.

### M2 — مسار الاستقبال الموقّع (tg-content-bot / PR #14)
مسار خارجي واحد `POST /ingest/signal` بنفس صيغة الأسلاك الموحدة للشركات (`x-vixor-timestamp`/`x-vixor-signature` على `${ts}:${body}`، نافذة ±5 دقائق، سقف 100KB، مقارنة timing-safe). الضمانات المنفذة حرفيًا من العقد: **fail-closed** (بلا سر → 503؛ بلا تقييم مخاطر صالح → 422 مُدقَّق)، **idempotency-first** عبر `idempotency_keys` (التكرار → 409 بلا أي أثر جانبي ثانٍ — T2)، القناة الهدف تُحسم **داخليًا من `app_settings.ingest_channel_id` فقط** ولا يُوثق أبدًا بوجهة قادمة من الحدث (§4)، المسودة تُنشأ عبر `createDraft` الحالي فوق source_post اصطناعي (`tg_chat_id="integration"`) وتظهر للمالك بنفس لوحة أزرار الموافقة الحالية — **لا ناشر ثانٍ**. الرد 202 يعني «حُفظ فقط» لا «أُرسل».

### M2b — إغلاق فجوة النتيجة غير المؤكدة (tg-content-bot / PR #15)
عند timeout/انقطاع بعد قبول تليجرام للرسالة: الرد المؤكد بخطأ (له `errorCode` في `api.ts`) = فشل معروف → مسار retry العادي (إعادة آمنة)؛ أي استثناء آخر (abort/شبكة/تحليل رد) = **نتيجة غير مؤكدة** → حالة `outcome_unknown` صريحة (migration 024) بمهلة 60 ثانية، ثم **مصالحة عبر سجل `telegram_updates`**: البوت أدمن في قنوات النشر فيستلم `channel_post` updates، فتُطابق بالقناة + `content_hash` بعد وقت المحاولة الفاشلة. إن وُجدت: تُسجل في `published_posts` برسالة تليجرام **الأصلية** ويُحذف صف الطابور — **صفر إرسال ثانٍ**. إن لم تُحسم بعد 5 محاولات: `dead_letter/outcome_unresolved` لقرار يدوي — الفشل الآمن أفضل من خطر التكرار.

### M3 — واجهة تقييم المخاطر (vixor-shield / PR #2)
`POST /assess` يلف المحرك الحالي `runScan` حرفيًا — **لا منطق مخاطر جديد**. الحماية: نفس HMAC، و**nonce لمرة واحدة** عبر جدول `assess_nonces` (migration 0006) لأن نافذة ±5 دقائق وحدها تسمح بإعادة الإرسال داخلها — وهو غير مقبول لقرارات المخاطر (عكس blocklist). خريطة المفردات تُغلق بند §8 المفتوح: LOW→allow، MEDIUM/INSUFFICIENT→review، HIGH/CRITICAL→reject، ونسبة المصادر < 60% (REQ-SH-SCAN-04) → `data_quality=incomplete` مع **ترقية allow إلى review** — أي لا يوجد مسار يرجع allow عند الفشل إطلاقًا، وأي استثناء من المحرك → review + `ENGINE_ERROR`. reason_codes آلية من معرفات العوامل الفعلية (S01..S12/E01..E12/U01..U07).

### M4 — مُنتج إشارة الاختبار (vixor-hunt / PR #1)
جسر إخراج واحد قابل لإعادة التشغيل بلا أي منطق اكتشاف جديد: `scripts/test-opportunity-fixture.json` (مصدر وحيد للهوية الثابتة `vixor-e2e-test-001`) + باني نقّي يبني المغلف §1/§2 مع تقييم §3 مضمّن + سكربت `emit-test-opportunity.mjs` صفر الاعتماديات يوقّع ويُرسل مع `--dry-run`. بوابة القبول مثبتة محليًا: تشغيلان متتاليان ينتجان **نفس** `publish:test:vixor-e2e-test-001` — الأول يُقبل 202 والثاني يُرفض 409 (T2). نسخة العقود المُضمَّنة في hunt مطابقة حرفيًا لنظيرتها في tg-content-bot (قاعدة المزامنة موثقة في رأس كل ملف).

## 4. اكتشافات التنفيذ

1. **ثغرة إنتاجية مكتشفة وأُصلحت (الأهم):** في `outbox-publish.ts` كانت `encodeURIComponent` تُطبق على `or=(...)` **كاملة بما فيها `or=`** — فيتحول `=` إلى `%3D` ويرى PostgREST **اسم بارامتر مشوهًا** بدل معامل `or=`. النتيجة: فلاتر claim/entry لم تكن تُطبق إطلاقًا — استعلام الدخول كان يعيد أي 5 صفوف بغض النظر عن الحالة، والـ claim كان يعمل فقط بفضل تحقق `lease_until` الرمزي بعد الـ PATCH (الـ workaround الذكي الذي حجب الخلل). أُصلح التشفير (التعبير وحده يُشفَّر) وبقي تحقق الـ token دفاعًا إضافيًا. هذا الاكتشاف وحده يبرر قيمة اختبارات M2b.
2. **bot-worker على Supabase لا D1** — أدلة الجرد الأولى (الجلسة السابقة) كانت صحيحة؛ كل كود M2/M2b كُتب عبر `getSupabase`/PostgREST بنفس أنماط المستودع.
3. **دلالة retry الصحيحة:** العقد §1 يطلب «retries reuse the same event and idempotency identifiers» — لذلك M4 يثبت `event_id` و`idempotency_key` معًا ويغير الطوابع الزمنية فقط.
4. **توأمية العقود موثقة لا سرية:** نسختان مُضمَّنتان (bot + hunt) من `@vixor/contracts` مع قاعدة مزامنة معلنة في رأس الملفين حتى تُعتمد الحزمة رسميًا كمصدر وحيد.

## 6. قائمة التشغيل الحي لإثبات T1 كاملًا (قرارات مالك فقط)

1. **تدوير الـ PAT فورًا** — البند 0 من قائمة التدوير؛ التوكن الحالي مر عبر المحادثة ولم يعد سرًا. أنشئ بديل fine-grained (Contents: read على مستودعات محددة فقط).
2. دمج/مراجعة المسودات الخمسة بالترتيب M1 → M2 → M2b → M3 → M4 (كلها CI أخضر وجاهزة للمراجعة).
3. `wrangler d1 migrations apply vixor-shield --remote` (migration 0006 للـ nonces).
4. تطبيق migration 024 على قاعدة tg-content-bot (توسيع قيد حالة `publish_outbox`).
5. `wrangler secret put INGEST_HMAC_SECRET` (قيمة واحدة أو سر لكل خدمة — الأخير أفضل) على tg-content-bot وvixor-shield.
6. تعيين `app_settings.ingest_channel_id` (معرف قناة الاختبار الداخلية) + `approval_chat_id` في قاعدة tg-content-bot، والتأكد أن البوت أدمن بنشر في قناة الاختبار.
7. نشر الفرعين المعدلين (tg-content-bot + vixor-shield) في بيئة الاختبار — **لا إنتاج**.
8. تشغيل T1: `node scripts/emit-test-opportunity.mjs --target https://<bot-host>/ingest/signal --secret $INGEST_HMAC_SECRET` → متوقع 202 + رسالة موافقة للمالك → موافقة بزر → **منشور واحد** في قناة الاختبار مع `tg_message_id` مسجل.
9. تشغيله ثانيًا → متوقع 409 (T2). ثم T7 (ضغط مزدوج على الزر) وT8 (إعادة تسليم webhook) حيًا.
10. توثيق النتائج بروتوكول §9 من وثيقة المطابقة (Task ID/المرحلة/PR/SHA/اختبارات/أثر/رجوع/حالة إغلاق).

## 7. ما لا يزال مؤجلًا عمدًا

- **دورة الدخل (أولويتك رقم 4):** click/conversion_pending/conversion_verified/commission_confirmed — تبدأ بعد نجاح T1–T9 الحي، والعقد §6 تصميمها بلا مستهلك بعد (لا ذكر لتحويلات أو عمولات في كود الـ worker إطلاقًا).

- الناشر التلقائي وpublish.ts القديم: لم يُلمسا — مسار التكامل يعمل بالتوازي معهما.
