## P2-0 — تدوير الأسرار (بوابة أمان، قبل أي حاجة أخرى)

| المهمة | التفاصيل | معيار القبول |
|---|---|---|
| إلغاء PAT الحالي | GitHub → Settings → Developer settings → Tokens → Revoke | محاولة استخدام التوكن القديم → 401 |
| PAT جديد مقيّد | إنشاء توكن جديد بنطاق `repo` فقط + مدة صلاحية ≤ 30 يومًا | التوكن الجديد يعمل على clone/push فقط |
| تدوير مفاتيح Cloudflare | Account API Tokens → rotate لكل توكن مستخدم في Workers | نشر `bot-worker` الجديد يعمل بالمفتاح الجديد |
| تدوير مفتاح بوت تيليجرام | BotFather → Revoke current token | setWebhook بالمفتاح الجديد → getWebhookInfo يرجع URL صحيح |
| تدوير مفاتيح Supabase | Rotate service_role + anon keys من Dashboard | المتغيرات البيئية محدثة في Workers/APP والاتصال يعمل |
| توليد `INGEST_HMAC_SECRET` | `openssl rand -hex 32` — لا يُرسل في أي محادثة | يُخزَّن مباشرة في `wrangler secret put` + مرجع في إدارة الأسرار |

**مالك البند:** المالك وحده (لا وصول للوحات التحكم). **الزمن المتوقع:** 30–45 دقيقة.

## P2-3 — التشغيل الحي الكامل T1 (جوهر إثبات دورة النشر)

الخطوات (قائمة تشغيل جاهزة — كل خطوة لها أمر قابل للنسخ):

1. `node scripts/emit-test-opportunity.mjs --dry-run` → عرض الحمولة الموقعة بلا إرسال.
2. الإرسال الفعلي → توقع **202** و`draft` جديد في لوحة الموافقة.
3. مراجعة قرار Shield `POST /assess` على نفس `correlation_id` → قرار مسجل بالسبب وTTL.
4. موافقة المالك من لوحة الموافقة → outbox claim → إرسال تيليجرام.
5. التحقق: **رسالة واحدة فقط** في قناة الاختبار + `published_posts` بصف واحد + `audit_events` سلسلة كاملة `correlation_id → request_id → message_id`.
6. **إعادة الإرسال نفس الحمولة حرفيًا** → توقع **409** بلا رسالة ثانية (الإثبات الحي للـ T2).

| معيار القبول | القياس |
|---|---|
| رسالة تيليجرام واحدة | عدّ رسائل القناة = 1 |
| صفر أثر ثانٍ في DB | `count(published_posts where correlation_id=X) = 1` |
| قرار Shield مسجل | سطر assess بالسبب وTTL قبل الموافقة |
| تدقيق قابل للتتبع | سلسلة correlation_id موحدة عبر الجداول الثلاثة |

**مالك البند:** المالك (الموافقة) + وكيل التنفيذ (الأوامر والقياس). **الزمن:** 30 دقيقة.

## P2-5 — دورة الإيراد على قناة واحدة (فتح أولوية 4)

المبدأ الحاكم: **الفصل الثلاثي** — نقرة ≠ تحويل ≠ عمولة مدفوعة. لا تُحسب عمولة قبل تأكيد التحويل من مصدر مستقل.

| المهمة | التفاصيل | معيار القبول |
|---|---|---|
| 5.a migration `conversions` | أعمدة: `click_id`, `post_id`, `affiliate_tag`, `conversion_event`, `amount`, `occurred_at`, `source` + فهرس فريد على `(source, conversion_event)` | migration مطبق على بيئة الاختبار |
| 5.b وسم الروابط الخارجة | `http/click.ts` يُلحق `post_id` + `click_id` (uuid) بكل رابط خارج من منشورات القناة التجريبية | كل نقرة تُنشئ صف `short_links` بمرجع كامل |
| 5.c نقطة استقبال تحويل | webhook صغير (PostgREST RPC أو مسار worker) يستقبل تحويل الشريك ويكتب في `conversions` بمرجع `click_id` | تحويل تجريبي يدوي → صف مطابق للنقرة |
| 5.d حساب العمولة | جدول نسبة لكل affiliate + عرض مسار: نقرة → تحويل → مبلغ مستحق | تقرير أسبوعي آلي لقناة واحدة بالأرقام الثلاثة مفصولة |
| 5.e تشغيل تجريبي | منشور واحد برابط شريك حقيقي في القناة التجريبية | أول سجل إيراد حقيقي موثق (حتى لو صفر تحويلات — المهم اكتمال السلسلة) |

**الزمن:** يوم عمل واحد. **شرط عدم التوسع:** لا إضافة قناة ثانية قبل اكتمال سلسلة واحدة موثقة من طرف لطرف.

## 1) لماذا هذه هي المرحلة التالية الصحيحة

- كل ما بنيناه في المرحلة 1 محلي ومُثبت بالاختبارات، لكن قاعدة «لا نشر إنتاج» تعني أن **القيمة الفعلية لا تتحقق إلا بالتشغيل الحي** تحت قياس صارم.
- P2-0 قبل كل شيء لأن أي بيئة حية بأسرار مكشوفة تُلغي قيمة كل الإثباتات السابقة.
- الإيراد آخرًا وليس أولًا: سلسلة الإشارة الموثوقة هي التي تُعطي قيمة للمنشور الذي يحمل رابط الشريك — عكس ذلك يعني قياس نقرات على محتوى غير موثوق.
